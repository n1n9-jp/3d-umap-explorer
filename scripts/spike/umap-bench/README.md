# scripts/spike/umap-bench

「ブラウザの中で UMAP を計算する」機能の方式を決めるための計測です（スパイク）。アプリ本体（`src/`・`public/`・ルートの `package.json`）には組み込みません。

比べた手段は 2 つです。いずれも、事前計算した kNN グラフから 3 次元の UMAP の最適化だけを Web Worker の中で行います。

- **embedding-atlas**（`embedding-atlas@0.26.0`、MIT、Apple）に含まれる、Rust 製の UMAP を WebAssembly にしたもの（以下 **atlas**）
- **umap-js**（`umap-js@1.4.0`、MIT、PAIR-code）。純粋な JavaScript（以下 **umap-js**）

## 結論（推奨）

**atlas を使うことを推奨します。** Worker の中で `run()` ではなく `step(チャンク)` と学習率の線形減衰で駆動し、チャンクごとにイベントループへ戻る形にします（理由と注意点は「推奨と実装時の注意点」）。

- 結果の質は 2 つとも、既存の事前計算（umap-learn）と区別がつきません（3 次元の 10 近傍の同ラベル率が 0.92 前後で一致）。選ぶ決め手は質ではなく、**メモリ・規模への強さ・中断のしやすさ・取り込みの手間**です。
- 速度は、1 万点・n=15・200 エポックでは umap-js のほうが速い（合計 6.0 秒 対 7.9 秒）。n=50 では逆転し（15.2 秒 対 12.2 秒）、7 万点（合成データ）では atlas のほうが n=15 で約 1.5 倍（74 秒 対 49 秒）、n=50 で約 2.9 倍（212 秒 対 73 秒）速くなります。
- メモリは atlas が umap-js の約 1/9〜1/12 です（1 万点・n=15：52 MB 対 451 MB。7 万点・n=50：413 MB 対 3.5 GB）。umap-js は 7 万点・n=50 で 3.5 GB を使い、一般的な端末のタブでは不安な量です。
- どちらも Worker で動かせば、計算中のメインスレッドの `requestAnimationFrame` の間隔は崩れません（27 条件のうち 26 条件で最大 16.8 ms。残る 1 条件は 33.4 ms、1 フレームの落ちが 1 回）。
- 弱みは、atlas の入口 `dist/umap.js` が package.json の `exports` にないこと（深い import になる）、Worker のバンドルが 1.3 MB（gzip 356 KB）あること、初期座標を外から渡せないことです。

## 環境と制約

- この実行環境（クラウドのコンテナ）で計測しました。CPU は Intel Xeon 2.3 GHz の 4 vCPU、GPU なし（ヘッドレス Chromium は CPU だけで動く）。**実機より遅い可能性があります。** 手段どうしの相対比較として読んでください。
- ブラウザは Playwright 1.63.0 の Chromium（`HeadlessChrome/157.0.8103.78`）。Node は v22.23.5（V8 12.4）。WebGL・WebGPU の実機、Firefox、Safari は未計測です。
- 計測した時刻の差による揺らぎがあります。同じ条件を別々のブラウザ起動で 2 回測った最適化の時間は 0.3〜1.8% の差でしたが、umap-js の初期化は起動ごとに 1.8〜2.7 秒の幅がありました（1 万点・n=15。表は平均）。

## 再実行の手順

```sh
cd scripts/spike/umap-bench
./run-all.sh          # 全工程。約 1 時間。ほかの重い処理を同時に走らせない
```

個別に実行するときは次のとおりです。`playwright` はこの実行環境にプリインストール済みのものを使います（`package.json` には入れていません）。

```sh
npm ci
python3 -m venv .cache/venv && .cache/venv/bin/pip install -r ../../precompute/requirements.txt
.cache/venv/bin/python make_knn.py --big   # kNN グラフ（入力は ../precompute の仕組みで .cache/ に取得される）
npx vite build && node size.cjs            # 計測ページのビルドとバンドルサイズ
node bench.cjs [--only <条件IDの正規表現>] [--force]   # ブラウザでの計測 → results/browser.json
node bench-node.cjs [--only ...] [--force]             # Node での計測 → results/node.json
node features.mjs                                      # 途中座標・中断・初期座標の確認 → results/features.json
.cache/venv/bin/python quality.py                      # 結果の質 → results/quality.json
node report.cjs > results/report.md                    # 表の生成
```

`.cache/`（kNN グラフ、埋め込みの座標、venv）と `node_modules/`、`dist/` はコミットしません。

## 計測の方法

| ファイル | 役割 |
|---|---|
| `make_knn.py` | MNIST 1 万点（784 次元）の**厳密な kNN**（k=50、自分自身を含む、ユークリッド距離）を Int32 の番号と Float32 の距離で書き出す。既存の事前計算と同じパラメータ（n_neighbors=15、min_dist=0.1、random_state=42）で umap-learn を実行し、その内部 kNN と厳密な kNN の先頭 15 列の一致率を出す。`--big` で 7 万点相当の合成データも作る |
| `src/` | 計測ページ。`main.js` が条件ごとに**新しい Worker** を作り、`worker-atlas.js` / `worker-umapjs.js` の中で kNN グラフの先頭 n 列から 3 次元の UMAP を計算する。メインスレッドでは `requestAnimationFrame` の間隔を記録する |
| `bench.cjs` | ヘッドレス Chromium でページを開いて条件を実行する。条件ごとにブラウザを起動し直す。計算中のブラウザ全プロセスの匿名メモリ（`/proc/*/status` の `RssAnon`）を 100 ms ごとに読んで、計測前からの増加量の最大値を出す |
| `node-run.mjs` / `bench-node.cjs` | Node で同じ計算（条件ごとに別プロセス）。時間とプロセスの最大 RSS の増加量 |
| `quality.py` | 結果の質（3 次元の k 近傍の同ラベル率など） |
| `features.mjs` | 組み込みやすさの項目の確認 |
| `size.cjs` | Vite が作った Worker バンドルの大きさ（圧縮前・gzip・brotli）と Wasm 本体の大きさ |
| `webgpu-check.cjs` | このブラウザで WebGPU が使えるか |

- **kNN の与え方**：厳密な kNN（k=50）の各行は距離の昇順なので、先頭 n 列がそのまま n 近傍です（列 0 は自分自身。umap-learn の `n_neighbors` も自分自身を数えるので同じ意味）。切り出しはメインスレッドで、rAF の計測区間の外で行います（7 万点の条件。1 万点の条件は区間内で行いましたが、最大フレーム間隔は 16.8 ms のままでした）。
- **点数**：1 万点（実データ）と 7 万点相当。7 万点は、MNIST の 1 万点を 7 回複製し、各複製に等方ガウス雑音（次元あたり σ=0.108、雑音のノルムが元の 15 近傍距離の中央値の 1/2）を加えた**合成データ**です（`make_knn.py` の `make_big`）。計算量（点数×次元×近傍数）を実データの 7 万点に揃えるためのもので、点群の構造は MNIST 全体とは異なります。厳密な kNN は 7 万点でも計算しています（55 秒）。
- **エポック数**：それぞれの既定と、200 に揃えた場合。既定は、atlas が 1 万点で **500**、7 万点で 200、umap-js が 1 万点・7 万点とも **200** でした（実測。umap-js は点数から決まる）。umap-js には 500 エポックも追加で測りました（atlas の既定と揃えるため）。
- **時間の区切り**：
  - 準備 ＝ Worker の起動（モジュールの取得と評価）＋ kNN の配列変換（umap-js だけ。`number[][]` にする）＋ 初期化（atlas：Wasm の読み込み・kNN からのグラフ構築・スペクトル初期化。umap-js：グラフ構築と検索用の構造の準備。初期座標は乱数）
  - 最適化 ＝ エポックの反復
  - 合計 ＝ 準備 ＋ 最適化。1 万点は別々の Worker で 2 回測った平均、7 万点は 1 回
  - 各回は**新しい Worker（コールド）**。同じ Worker での 2 回目（ウォーム）は別表に出しています。
- **乱数の種**：atlas は `seed: 42`、umap-js は `random` に mulberry32（種 42）を渡しました。
- **rAF**：計算を始める直前から結果が返るまでの間隔の中央値・95 パーセンタイル・最大。ベースライン（アイドル時）は 16.7 ms で、メインスレッドを 200 ms 止めると最大 183 ms になることを確認しています（計測が止まりを検出できる）。
- **結果の質**：3 次元で各点の k 近傍（自分を除く、k=10 と 15）のうち同じラベル（`public/data/mnist/labels.u8`）を持つ割合の全点平均。既存の事前計算（`public/data/mnist/positions.f32`）を同じ指標で測ると 10 近傍で 0.9215 でした（調査の 0.92 と一致）。あわせて、(a) 高次元の厳密な 15 近傍が 3 次元の 15 近傍に含まれる割合（再現率）、(b) ラベルごとの重心どうしの距離 45 組の既存の事前計算との相関（数字の並びが同じか）を出しました。
- **ハーネスの版**：条件の追加と修正を重ねて測りました。7 万点・step 方式・中断の条件は最終版のハーネスで、1 万点の主な条件はその前の版で測っています（違いは、rAF の計測区間にメインスレッドでの切り出しが入るか、`yieldEvery` を渡せるか、だけで、準備・最適化の時間は Worker の中で測っているので同じ手順です）。

### kNN グラフの用意の結果

- 厳密な kNN（k=50）：1.8 秒で計算（numpy の行列積）。同一点（距離 0 の別の点）はありませんでした。
- umap-learn（0.6.0、`compatibility_layout=True`）の内部 kNN（pynndescent の近似）と、厳密な kNN の先頭 15 列（自分自身を含む）の一致率は **99.58%**（自分自身を除く 14 列で 99.55%）。15 列すべてが一致した点は 95.2%。厳密な 15 番目の距離に対する umap-learn の 15 番目の距離の比の平均は 1.0002 です。したがって、厳密な kNN を使っても、既存の事前計算とほぼ同じグラフになります。
- この環境で umap-learn を同じパラメータで再実行すると、`public/data/mnist/positions.f32` と**ビット単位で一致**しました（最大差 0.0）。

### 表の読み方と注意

- 「準備」と「最適化」は、1 万点は 2 回、7 万点は 1 回の測定です。7 万点の atlas は、既定のエポック数が 200 で「200 に揃えた条件」と同じ設定になるため、同条件の再測定が 2 行あります（合計 49.2 秒と 47.1 秒、73.7 秒と 72.2 秒で、差は 4% 以内）。
- 「メモリ増」は、計算中のブラウザ全プロセスの匿名メモリの増加量の最大値です。Worker 単体の値ではありません（Worker 内では `performance.memory` が使えません）。kNN の配列（k=50 で 1 万点が 4 MB、7 万点が 28 MB）と結果の座標を持つメインスレッドの分を含みます。umap-js は `number[][]` で kNN とグラフを持つため、点数と n に比例して大きくなります。
- 「Node 合計」は、同じ計算を Node で 1 回測った値です。**atlas はブラウザと Node でほぼ同じ時間**（0.94〜1.06 倍）ですが、**umap-js は Node のほうが 1.3〜2 倍遅い**（V8 の版の違い：Node 22 は V8 12.4、このブラウザは Chromium 157）。つまり、Node で測った umap-js の時間（調査時の「初期化 4.3 秒、最適化 13.4 秒」など）は、現在のブラウザでの値より悲観的です。選定には、ブラウザでの値を使うべきです。
- 7 万点の結果の質（同ラベル率）は、合成データの複製が近傍に入るため、比較の根拠になりません。時間とメモリの規模感として読んでください。
- ブラウザの値は、新しい Worker（コールド）の平均です。同じ Worker での 2 回目（ウォーム）は、atlas は準備が短くなり（Wasm のコンパイル済み：0.70→0.48 秒）、umap-js は準備が長くなります（1.85→2.41 秒。メモリが残っているため）。最適化の時間は変わりません。

### 結果の質

- 1 万点では、**どの手段・条件でも、既存の事前計算と同じ水準**です（10 近傍の同ラベル率：既存 0.9215、atlas 0.921〜0.922、umap-js 0.921、n=50 では 0.913〜0.916）。n=50 で少し下がるのは近傍を広げたことによるもので、手段の差ではありません。
- エポック数は、1 万点では 200 で足ります（atlas：500 エポック 0.9211、200 エポック 0.9219）。
- ラベル重心の配置（数字の並び）は、既存と相関 0.93〜0.97 で、どの手段でも既存とほぼ同じ並びになります。atlas の初期化を `random` にすると 0.88 に下がる（同ラベル率は 0.9225 で変わらない）ので、スペクトル初期化は全体の配置を安定させる効果がありそうですが、1 つの種での結果なので断定はしません。umap-js はスペクトル初期化がなく、初期座標は [-10, 10] の一様乱数ですが、配置の相関は 0.94 でした。
- `step()` を学習率一定のまま回すと質が大きく落ちます（同ラベル率 0.83）。`run()` と同じ質にするには、チャンクごとに学習率を線形に下げる必要があります（下の「step 方式」）。

### step() 方式と中断

`run()` は Wasm の中で最後まで一括で実行されます。`step(n)` と `setParameters({ learningRate })` を使えば、途中の座標の読み出しと中断ができます。この表の `stepdecay` は、チャンク（10 エポック）ごとに `learningRate = 1 − 完了エポック / 全エポック` を設定してから `step(10)` を呼ぶ方式です（`src/atlas-run.js`）。`noyield` は Worker のイベントループへ戻らない場合、`yield` は 1 チャンクごとに `MessageChannel` でマクロタスクへ戻る場合です。中断の確認は、計算の開始から 2 秒後（umap-js は 3 秒後）に Worker へ `cancel` メッセージを送り、停止までの時間を測りました。

- **`step` の `await` だけでは Worker がメッセージを受け取れません**（`noyield` の行：`cancel` は完了まで処理されない）。`yield` を挟むと、チャンクの途中で送ったメッセージは次のチャンクの終わりで処理され、67 ms で止まりました（最悪でも 1 チャンクの時間：10 エポックで約 0.4 秒）。umap-js も同じで、5 エポックごとに戻して 44 ms で止まりました。
- 途中の座標は、`step` の後に `embedding` を読むと得られます（20 回受信、初回は計算開始の約 0.9 秒後）。
- `run()` のときは、進捗は `progress` コールバックの中から `postMessage` すれば届きますが、座標は届きません（`run()` の間 `embedding` は更新されない）。

## 推奨と実装時の注意点

### 推奨：atlas を Worker の中で `step` ＋ 学習率の減衰で駆動する

理由は次のとおりです。

1. **メモリと規模**：umap-js は kNN とグラフを `number[][]` やオブジェクトで持つため、点数と n に比例してメモリが急に増えます（1 万点・n=50 で約 1 GB、7 万点・n=50 で約 3.5 GB）。atlas は 7 万点・n=50 でも 413 MB です。n_neighbors を利用者が変えられる機能では、n=50 を許すかどうかで差が決定的になります。準備の時間も、7 万点・n=50 で umap-js が 120 秒、atlas が 10 秒です。
2. **速度**：1 万点・n=15 だけは umap-js が約 25% 速い（6.0 秒 対 7.9 秒）ものの、n=50 で逆転し（15.2 秒 対 12.2 秒）、規模が大きいほど差が開きます。1 万点・n=15 の差のために 2 つの経路を持つ複雑さは見合わないと判断します。
3. **中断と途中経過**：`step(1〜10)` と学習率の減衰（`1 − 完了 / 全体`）で、`run()` と同じ質（`stepdecay` チャンク 1 で同ラベル率 0.921、チャンク 10 で 0.919。`run()` は 0.922）のまま、停止と途中座標の表示ができます。`run()` の最適化 7.18 秒に対して、チャンク 10 で 7.6〜7.9 秒（+6〜10%）、チャンク 1 で 8.07 秒（+12%）です。
4. **再現性**：同じ種でブラウザと Node のビットが一致するので、サーバー側での検証や、Playwright の検証に使えます（umap-js は Node と一致しない）。
5. **描画への影響**：どちらも Worker で動かせば、メインスレッドの rAF は崩れません（27 条件のうち 26 条件で最大 16.8 ms）。

### 実装時の注意点

- **取り込み方**：`embedding-atlas/dist/umap.js` は `exports` にないため、`resolve.alias` で実ファイルを指すか、`dist/umap.js` と `dist/chunk-Bn3LaujC.js` の 2 ファイルを `src/` 配下へコピー（ベンダリング）します。`npm install embedding-atlas` は必須の peer を入れて約 100 MB 増えるので、コピーのほうが軽い。どちらでも版を `0.26.0` に固定し、**簡単な計算を実行して座標が出ることを確かめる単体テスト**を置いて、版の更新で入口が変わったことに気づけるようにしてください。コピーする場合は、リポジトリの LICENSE（MIT）の表記を上流で確認して同梱してください（パッケージには LICENSE ファイルがない）。
- **遅延読み込み**：Worker のバンドルは 1.3 MB（gzip 356 KB、brotli 265 KB）あります。UMAP の計算を使うときに初めて Worker を作る（動的 import）ようにして、通常の起動の読み込みに含めないでください。
- **Worker の中の手順**：`createUMAPFromKNN(count, 3, idx, dist, { seed, minDist, nEpochs: 200 })` → 少数のエポックのチャンクごとに `setParameters({ learningRate: 1 − done/total, repulsionStrength: 1, negativeSampleRate: 5, minDist, spread: 1 })`、`await step(chunk)`、`postMessage(座標のコピー)`、**`MessageChannel` などでマクロタスクへ戻る**。最後の手順がないと `cancel` が届きません。`setParameters` には 5 項目をまとめて渡しました（測った構成。項目を省くと既定に戻るかどうかは未確認）。
- **エポック数**：atlas の既定は 1 万点で 500（約 19 秒）、7 万点で 200 です。1 万点では 200 で質が変わらない（同ラベル率 0.9219 対 0.9211）ので、明示的に 200 を渡して時間を 6 割減らします。
- **kNN の配信**：厳密な kNN（k=50）の先頭 n 列で、umap-learn の近似 kNN と 99.6% 一致し、質も同じです。1 万点 × 50 は、番号を Uint16 で 1 MB、距離を Float32 で 2 MB（点数が 65,536 を超えるなら番号は Uint32）。Worker の中で `Int32Array`・先頭 n 列に切り出してから渡します（`src/knn.js` の `sliceKnn`）。
- **`min_dist` の変更**：`setParameters({ minDist })` ＋ `reset()` でグラフの再構築を省けます。`n_neighbors` の変更は新しいインスタンスを作ります（準備は 1 万点で約 1 秒）。
- **利用者が結果を待つ時間**：この環境（CPU のみ・4 vCPU）で 1 万点・200 エポックが、n=15 で約 8 秒、n=50 で約 12 秒です。実機では短くなる可能性がある（未計測）ので、途中座標を 10 エポックごとに表示する設計にして、待ち時間を体感で短くしてください。
- **今の既存配置との連続性**：atlas は初期座標を外から渡せません。利用者が `n_neighbors` を変えたとき、現在の配置から出発して見た目を保つ（ウォームスタート）機能が必要なら、atlas では実現できません。その場合は、(a) 結果を現在の配置へ相似変換（Procrustes）で合わせる、(b) umap-js を使う（内部配列の書き換え。版の固定が必要）、のどちらかを検討してください。
- **umap-js を使う場合の目安**：1 万点・n≤15 に限るなら実用的で、バンドルは 24 KB（gzip）と軽い。ただし、Node ではブラウザの 1.3〜2 倍遅いため、サーバー側の値で見積もらないこと。n=50 以上や 3 万点以上では、準備だけで数十秒かかり、メモリが 1 GB を超えます。

## 未計測・限界

- **実機**：この環境の CPU の値のみで、実機のブラウザでの速度は未計測です。Firefox・Safari・モバイルも未計測（Wasm の結果が Chromium と一致するかも未確認）。
- **WebGPU（atlas の `gpu: true`）**：実 GPU がなく、速度は**未計測**です。SwiftShader 上で完走することだけを確認しました（50 エポック、1 万点、n=15。CPU と結果は一致しない）。実機で大幅に速くなる可能性があります。
- **7 万点**：MNIST の実データではなく合成データ（1 万点の複製＋雑音）で、1 回の測定です（atlas は同条件を 2 回）。質の評価はしていません（参考値のみ）。MNIST の 7 万点の実データは、この環境の入力の仕組み（`scripts/precompute/`）が 1 万点のみのため使っていません。
- **メモリ**：ブラウザ全プロセスの匿名メモリの増加量の最大値で、Worker 単体ではありません。Node は `process.resourceUsage().maxRSS` の増加量で、`results/node.json` にあります（最大値で、ガベージコレクション前の値を含みます）。
- **umap-js の `min_dist` だけの変更**：未確認。
- **`setParameters` の部分指定**：atlas の `setParameters` に一部の項目だけを渡した場合に残りがどうなるかは未確認です（5 項目を毎回渡しました）。
- **複数の種・複数回の質の分散**：質は種 42 の 1 回の結果です。種による揺れは測っていません（既存の事前計算との比較は、1 つの種どうしの比較）。
- **ハーネスの版**：1 万点の主な条件は、7 万点の条件より前の版のハーネスで測っています（上の「計測の方法」の最後を参照）。`./run-all.sh` で全条件を最終版で取り直せます。
